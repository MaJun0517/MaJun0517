# company-research · 企业/行业调研报告生成底座

> 输入公司名（可选行业词），一键生成行业调研报告（公司概况融入行业章节），Word 文档直接可用。

## 一、项目概述   https://github.com/MaJun0517/company-research

面向**投资研究、行业分析、企业 BD 尽调**场景的"自动化调研报告"生产底座。它把"搜资料 → 读资料 → 写报告 → 排版成 Word"这条高度依赖人工的研究流程，做成了一条「**规范查询 → 多源降级采集 → 结构化抽取 → 双产物组装 → 会话内 LLM 撰写 → Word 专业化排版**」的自动化流水线，输出单份可交付的 `.docx` 行业调研报告。

报告模板（`prompts/industry_report.md`）将公司概况内容（经营表现、市场地位、商业模式、风险）揉进对应行业章节（对标分析 / 风险与趋势等），不单独成章，最终交付一份 10 章节、有数据有来源的行业研究报告。

## 二、业务背景与痛点

行业研究分析师生成一份"XX 公司行业调研报告"，传统流程通常要 1-2 天，且依赖多个外部网站（新闻、年报、监管、研报、知乎/雪球等），暴露三个核心问题：

- **资料分散、采集成本高**：分析师在搜索结果页逐条点开→读→复制，年报 PDF 几十页靠肉眼筛核心数据（营收/净利/毛利率/扣非等），人工耗时占全流程 60%+。
- **来源不可靠、易断网/超时/被反爬**：搜索/抓取/解析三段链路任一节点挂掉都要手工补；多源数据口径不齐，分析师要在多份资料间"对齐事实"。
- **报告排版耗时、专业度受限**：md 转 docx 的二级标题序号、表格列宽、目录页码、页眉页脚、表头跨页重复等排版细节手工难以标准化，输出质量依赖个人熟练度。

## 三、整体架构

| 层 | 角色 |
|---|---|
| 入口 `collector.py` | CLI + 公共 API（`collect` / `write_facts` / `detect_gaps` / `supplement_section` / `clean_work`） |
| 采集包 `collect/` | 13 个单职责模块：`spec` 查询规范 / `search` 搜索 / `fetch` 抓取 / `pdf` PDF 解析 / `extract` 结构化抽取 / `pipeline` 编排 / `cache` 缓存 / `http` 共享 HTTP / `anysearch` RPC / `text` 文本工具 / `assemble` 组装 / `config` 配置 / `log` 日志 |
| 转换 `converter.py` | Markdown → Word：封面/目录/页码/页眉/表格/自动中文序号 |
| 模板 `prompts/industry_report.md` | 10 章节报告结构（摘要→行业定义→市场规模→政策→竞争→技术→商业模式→对标→风险→趋势） |
| 产物 `output/*.docx` | 交付：`<公司>_行业调研.docx`（中间产物 `facts.md` / `facts.json` 在 `.work/`，完成后清理） |

技术栈：Python 3.10+、标准库 `urllib` + `python-docx` + `markitdown[pdf]`。外部数据源：anysearch（搜索，JSON-RPC）/ crawl4ai（Docker 容器，深抓与本地 LLM 抽取）/ firecrawl（云抓取 + json 抽取，可选按量计费）。

## 四、核心功能模块

### 1. 章节级查询规范（`collect/spec.py`）

把行业调研抽象成 9 个章节（行业定义/规模/政策/竞争/技术/商业模式/对标/风险/趋势），每章节 1-4 条查询模板，用 `{company}` / `{year}` / `{prev_year}` / `{industry}` 占位符运行时替换。`vertical` 标记垂直域（`finance` / `business`），由 `AnysearchSearcher.resolve_vertical` 自动挑选 sub_domain；无 `industry` 时带 `{industry}` 的纯行业查询自动跳过。一次采集覆盖"公司面 + 行业面"，避免章节被公司报道占满缺全景。

### 2. 三级降级采集链

每一段都"主+备+末位"三级降级，任何单一服务挂掉/欠费都自动往下走，全链路永不断流：

- **搜索**：anysearch `batch_search` 并行（≤5/批，章节级并发）→ 兜底 firecrawl `/v2/search`
- **抓取 HTML**：crawl4ai `/crawl` 批量（必须带 `crawler_config: {wait_until: domcontentloaded, page_timeout: 20000}`，默认等 networkidle 90s/页慢两个数量级）→ 兜底 firecrawl `/scrape` → 末位 anysearch `extract`
- **PDF 解析**：markitdown 本地（SSL 容忍 + 2^n 退避）→ 兜底 firecrawl `/scrape`
- **结构化抽取**：firecrawl `/v2/scrape` 的 json format（云端 LLM + JSON Schema）｜ crawl4ai `/llm`（本地 DeepSeek 切换，免费）

### 3. firecrawl 成本护栏 + 402 毒化（`collect/http.py`）

firecrawl 按量计费，所以做了两层保护：`Budget` 类线程安全计数，总调用封顶 `MAX_FIRECRAWL_CALLS`（默认 12），并**为最高价值的"结构化抽取"阶段预留 `reserve` 配额**（普通搜索/抓取只能用到 `limit - reserve`），关键时刻永远有额度；一旦遇 HTTP 402（余额耗尽），`_mark_fc_poisoned()` 立即把本次运行"毒化"，后续所有 firecrawl 调用短路抛错，不再空耗一分钱。

### 4. 质量×相关性打分选源（`collect/extract.py` + `pipeline.py`）

深抓名额（默认 8 URL）和抽取配额都稀缺。`score_source` 对财务机构域加分、视频社交减分；**无目标品牌信号但疑似别家上市公司年报的 URL 直接 -6 强降权**，避免搜"私人公司"时把宝贵的深抓/抽取配额全烧在无关年报上。`_pick_targets` 每章节配额封顶 + 全局 `质量×相关性` 排序取前 N。

### 5. 智能截断 + 文本清洗（`collect/text.py`）

- `smart_truncate`：保留开头 + 财务关键词（营业收入/净利润/毛利率/扣非…）命中最多的段落，**不做一刀切前 N 字符**；
- `strip_nav_links`：去站内导航菜单行（整行都是短标签链接的识别为菜单，正文段落通常含其它文字）；
- `clean_pdf_fragments`：去 PPT 转 PDF 的乱序单字碎片行（最长连续 CJK run ≥3 才保留为可读中文行）。

### 6. 品牌词提取（`company_brand`）

从"北京杉数智能科技有限公司"剥出"杉数"，靠地域前缀表（30+ 城市）+ 公司后缀表（股份有限公司/有限公司/集团/科技/智能…）循环剥离；提取结果用于来源相关性判断和"该公司有无公开财务数据"信号。

### 7. 磁盘缓存自动失效（`collect/cache.py`）

key = `sha1(CACHE_VERSION + 查询 + 当天日期)`，24h TTL。`CACHE_VERSION`（当前 v4）在清洗/截断策略变更时手动递增，让旧缓存整体失效，不依赖时间。分三类：搜索（按 `report_type + section + query`）/ 抓取（按 URL）/ 抽取（按 `report_type + section + company + 来源 URL 哈希`）。

### 8. 配置优先级链（`collect/config.py`）

`环境变量 > 项目 .env > anysearch skill .env > 默认值`，且空值不覆盖已配置项。所有密钥（`ANYSEARCH_API_KEY` / `FIRECRAWL_API_KEY` / `CRAWL4AI_API_TOKEN`）只从 `.env` 读，代码零硬编码。

### 9. 双产物 + 来源统计（`collect/assemble.py`）

`facts.md` 与旧版兼容，`facts.json` 附带 `stats`（各 provider 调用次数、缓存命中）和 `timing`（各阶段耗时），**给撰写阶段的 LLM 判断数据可信度用**，而不仅给人看。

### 10. converter 的 Word 专业化（`converter.py`）

不只是"md 塞进 docx"：Word TOC 域缓存章节列表（打开即可见，F9 刷新页码）、**自动中文序号**（一、/（一）/1./（1）且智能剥掉手写序号避免重复）、表头跨页重复（`w:tblHeader`）、按内容长度启发式分配列宽（每列 ≥2cm）、首行缩进 2 字符、页眉底部深蓝细线 + 页码"第 X 页"从正文重排。链接渲染为"文字 (域名)"去噪。

## 五、量化成果

- **报告生成耗时压缩**：从分析师手工 1-2 天压缩到 5-10 分钟（9 章节采集 + 撰写 + 排版一次完成）。
- **多源降级链保证永不断流**：主服务挂掉/欠费自动降级到本地免费能力，单次采集即使 firecrawl 完全停用（`ENABLE_FIRECRAWL=false`）全链路仍可跑通。
- **深抓速度提升两个数量级**：crawl4ai 加 `crawler_config: domcontentloaded + 20s 超时`后，8 页深抓从 12+ 分钟降到 1 分钟内。
- **PDF 数据有效信息密度提升**：智能截断 + 版式碎片清洗 + 财务关键词优先保留，让年报 PDF 解析后的有效字段命中率显著提升。
- **重复采集零成本**：磁盘缓存 24h 内同查询不重复请求，调试期反复跑也是秒级响应。
- **报告排版 0 人工**：自动中文序号、TOC 域、表格列宽、页眉页码全部自动化，输出可直接交付。

## 六、个人职责

独立完成从架构设计到落地实现的全流程：

- 架构层面：4 层职责划分（入口/采集/转换/模板）+ 13 个采集模块的单一职责边界
- 工程层面：firecrawl 成本护栏（Budget + reserve 预留 + 402 毒化）、三级降级链、质量×相关性打分选源、智能截断与文本清洗、品牌词提取、缓存自动失效
- 体验层面：converter 的 Word 专业化（TOC 域、自动中文序号、表头跨页、差异化列宽、首行缩进）、CLI 公共 API 与旧版兼容
- 流程层面：报告生成完全在会话内完成（不依赖 `claude -p` 子进程），并把"采集失败返回 None / 让上层走 WebSearch 兜底"的契约写进 pipeline
