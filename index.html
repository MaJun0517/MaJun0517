🏢 广东海圆圆农业科技有限公司 🧑‍💻 AI 全栈开发（实习） 🗓 2026.05 – 至今
项目概述

面向食材配送、食堂承包、团餐、农产品贸易企业的政府采购商机平台。把企业"找标—评标—跟标—复盘"这条高度依赖人工的经营流程，做成「采集 → 治理 → 分析 → 投标管理 → AI 决策」的自动化闭环，覆盖从发现商机到报价决策、流程推进、经验沉淀的完整链路。

业务痛点
  • 找标 · 漏标：公告分散在中国政府采购网、地方公共资源交易平台等多个渠道，栏目列表又有滚动窗口，人工刷站频率跟不上，中间的公告说漏就漏。
  • 找标 · 筛选难：每天新增公告成百上千，多数与本企业资质、经营范围、配送半径无关，靠人眼逐条翻，高价值食堂标被淹没在噪音里。
  • 评标 · 报价无依据：报价是评分核心，却缺少历史中标价、竞争对手报价与预算区间做参考，只能凭经验拍板，报高失标、报低亏本。
  • 评标 · 响应窗口短：从公告发布到投标截止常不足 20 天，还要同步准备资质、报价、配送方案与保证金，判断慢一步就来不及。
  • 跟标 · 跟踪混乱：一条标要经历澄清、更正、开标、中标结果、废标等关联公告，散落在各人的 Excel 与群消息里，交接即丢失。
  • 跟标 · 节点易错过：保证金缴纳、答疑提交、投标文件递交、开标多个时间点靠人记，错过一个即前功尽弃。
  • 复盘 · 数据不准：预算单位（元 / 万元 / 大写金额）混乱、公告时间与服务器时间时区口径不一、跨渠道重复公告，导致紧迫度、今日新增、中标率等统计经常算错。
  • 复盘 · 经验无沉淀：失标原因、竞争对手情报没有结构化沉淀，第二年同类标重复踩坑。

分拣打标签系统 实习交付

面向农产品分拣车间、对接企业 ERP 的称重 / 打印 / 扫码桌面应用，覆盖从称重到回传入库的完整闭环。

🏢 广东海圆圆农业科技有限公司 🧑‍💻 AI 全栈开发（实习） 🗓 2026.05 – 至今
项目概述

面向农产品（果蔬等）分拣车间的 WPF 桌面系统，把"称重 → 打印标签 → 回传 ERP → 确认入库"这条原本高度依赖人工的流程，做成实时、可追溯、与 ERP 强一致的自动化流水线。系统以 .NET (C#) + WPF 开发，采用 net10.0-windows / .NET Framework 4.8 双目标编译，一套代码同时覆盖 Win10 与 Win7 生产机；日均处理订单行 2000+，10 台生产设备稳定运行。

业务痛点
  • 效率低：称重与录单割裂，称重靠人、录单靠专人（原需 2 人 × 4 小时/天），一批完成后才能补录，时效差。
  • 易出错：手工抄录 + 二次录入，且单位常混用（销售按公斤、采购按斤），曾出现"采购斤单回传 kg 记成实际一半"的账面错误。
  • 难追溯：标签无统一编码，出库后无法反查是哪一单、哪一批。
  • 设备旧、硬件杂：10 台生产机含大量锁死系统的 Win7（无法升级 .NET 10），电子秤又有串口、蓝牙、USB 键盘等多种型号，难以统一接入。
核心功能
  • 01
    称重采集

    接入四类电子秤，自研 ASCII 帧解析器一个入口兼容 3 种协议（首衡 / TWI / 通用数字帧）；支持手动输入、逐袋累重，重量优先级"手动 > 累重 > 秤读数"。

  • 02
    打印标签

    预览确认 → 驱动打印；17 个字段每字段可自定义字号；自绘 Code128 条形码（Code B/C 自动切换 + mod103 校验），标签扫码即可定位原订单；支持已分拣订单补打。

  • 03
    扫码追溯

    物理扫码枪（键盘楔入、免探测）自动输入定位订单，与标签条码形成"打印 → 扫码 → 反查"闭环。

  • 04
    ERP 回传

    称重回传 + 分拣确认 + 采购确认入库，销售 / 采购双数据源切换；失败自动入待重传队列、登录自动补传，杜绝"打印成功但 ERP 无数据"。

  • 05
    硬件配置

    四标签触屏设置页，探测并选择设备（免硬编码型号），串口参数 / 打印模板 / 小数位 / 明暗主题均可配。

  • 06
    可靠性与部署

    打印前离线 / 暂停队列预检防"假成功"；DPAPI 加密本地存储（会话 / 凭据 / 待重传队列 / 设备历史）；Inno Setup 安装包 + 双通道半自动更新（版本比对 + SHA256 校验）。

项目概述

面向网络内容创作者的热点情报系统。把创作者每天"盯热榜—翻新闻—找选题—做分析"这条高度依赖人工的流程，做成「采集 → 加工 → 分析 → 检索 → 推送」的自动化闭环，解决"多平台信息碎片化、原始榜单无分析、缺乏创作辅助"三大痛点。

业务痛点
  • 信息碎片：热榜分散在多个平台，官方新闻与热点话题割裂，来回切换耗时。
  • 只有榜单没有分析：原始榜单只是标题列表，创作者需要自己判断趋势、情感、关键词和上升话题。
  • 缺乏创作闭环：除了看，还要能对话追问、找相似选题、导出报告、推送到飞书协作。
核心功能
  • 01
    多后端采集引擎

  • 02
    双模块数据体系

    按平台分类分流为热榜模块（写 HotArticle，按热度排序）与新闻模块（写 NewsItem，按重要度排序），两套模型 / 索引 / 向量语义隔离；upsert + 下榜删除 + 热度快照（HeatSnapshot），支持上升话题识别。

面向投资研究、行业分析、企业 BD 尽调场景的"自动化调研报告"生产底座。把"搜资料 → 读资料 → 写报告 → 排版成 Word"这条高度依赖人工的研究流程，做成「规范查询 → 多源降级采集 → 结构化抽取 → 双产物组装 → 会话内 LLM 撰写 → Word 专业化排版」的自动化流水线，输出单份可交付的 .docx 行业调研报告。报告模板将公司概况（经营表现、市场地位、商业模式、风险）揉进对应行业章节，不单独成章，最终交付一份 10 章节、有数据有来源的行业研究报告。

业务痛点
  • 资料分散、采集成本高：分析师在搜索结果页逐条点开→读→复制，年报 PDF 几十页靠肉眼筛核心数据，人工耗时占全流程 60%+。
  • 来源不可靠、易断网 / 超时 / 被反爬：搜索 / 抓取 / 解析三段链路任一节点挂掉都要手工补；多源数据口径不齐，要在多份资料间"对齐事实"。
  • 报告排版耗时、专业度受限：md 转 docx 的二级标题序号、表格列宽、目录页码、页眉页脚、表头跨页重复等细节手工难以标准化。
核心功能
  • 01
    章节级查询规范（spec.py）

    把行业调研抽象成 9 个章节（行业定义 / 规模 / 政策 / 竞争 / 技术 / 商业模式 / 对标 / 风险 / 趋势），每章节 1-4 条查询模板，用 {company} / {year} / {industry} 占位符运行时替换；vertical 标记垂直域自动挑选 sub_domain，无 industry 时纯行业查询自动跳过。

  • 02
    三级降级采集链

    每段都"主 + 备 + 末位"三级降级，任一服务挂掉 / 欠费都自动往下走，全链路永不断流：搜索 anysearch batch_search 并行（≤5/批，章节级并发）→ firecrawl；抓取 crawl4ai /crawl 批量（domcontentloaded + 20s 超时）→ firecrawl → anysearch extract；PDF 解析 markitdown 本地 → firecrawl；抽取 firecrawl json format ｜ crawl4ai /llm 本地 DeepSeek。

  • 03
    firecrawl 成本护栏 + 402 毒化

    按量计费因此加两层保护：Budget 类线程安全计数，总调用封顶（默认 12），并为最高价值的"结构化抽取"阶段预留 reserve 配额；一旦遇 HTTP 402（余额耗尽）立即把本次运行"毒化"，后续所有 firecrawl 调用短路抛错，不再空耗。

  • 04
    质量×相关性打分选源

    深抓名额（默认 8 URL）与抽取配额都稀缺：score_source 对财务机构域加分、视频社交减分，无目标品牌信号但疑似别家上市公司年报的 URL 直接 -6 强降权；每章节配额封顶 + 全局质量×相关性排序取前 N。

  • 05
    智能截断 + 文本清洗

    smart_truncate 保留开头 + 财务关键词命中最多的段落，不做一刀切；strip_nav_links 去站内导航菜单行；clean_pdf_fragments 去 PPT 转 PDF 的乱序单字碎片行。

  • 06
    品牌词提取

    靠地域前缀表（30+ 城市）+ 公司后缀表循环剥离，从"北京杉数智能科技有限公司"剥出"杉数"；提取结果用于来源相关性判断和"该公司有无公开财务数据"信号。

  • 07
    磁盘缓存自动失效

    key = sha1(CACHE_VERSION + 查询 + 当天日期)，24h TTL；CACHE_VERSION（当前 v4）在清洗 / 截断策略变更时递增让旧缓存整体失效。分搜索 / 抓取 / 抽取三类缓存。

  • 08
    配置优先级链

    环境变量 > 项目 .env > anysearch skill .env > 默认值，且空值不覆盖已配置项；所有密钥只从 .env 读，代码零硬编码。

  • 09
    双产物 + 来源统计

    facts.md 与旧版兼容，facts.json 附带 stats（各 provider 调用次数、缓存命中）与 timing（各阶段耗时），给撰写阶段的 LLM 判断数据可信度用。

  • 10
    converter Word 专业化

    不只是 md 塞进 docx：TOC 域缓存章节列表（打开即可见，F9 刷新页码）、自动中文序号（一、/（一）/1./（1）且智能剥掉手写序号）、表头跨页重复、按内容长度启发式分配列宽（每列 ≥2cm）、首行缩进 2 字符、页眉底部深蓝细线 + 页码从正文重排。

量化成果
  • 报告生成耗时从分析师手工 1-2 天压缩到 5-10 分钟（9 章节采集 + 撰写 + 排版一次完成）
  • 多源降级链永不断流：即使 firecrawl 完全停用（ENABLE_FIRECRAWL=false）全链路仍可跑通
  • 深抓速度提升两个数量级：crawl4ai 加 domcontentloaded + 20s 超时后，8 页深抓从 12+ 分钟降到 1 分钟内
  • 报告排版 0 人工：自动中文序号、TOC 域、表格列宽、页眉页码全部自动化，输出可直接交付
个人职责
  • 架构层面：4 层职责划分（入口 / 采集 / 转换 / 模板）+ 13 个采集模块的单一职责边界。
  • 工程层面：firecrawl 成本护栏、三级降级链、质量×相关性打分选源、智能截断与文本清洗、品牌词提取、缓存自动失效。
  • 体验层面：converter 的 Word 专业化排版、CLI 公共 API 与旧版兼容。
  • 流程层面：报告生成完全在会话内完成（不依赖 claude -p 子进程），并把"采集失败返回 None / 让上层走 WebSearch 兜底"的契约写进 pipeline。
